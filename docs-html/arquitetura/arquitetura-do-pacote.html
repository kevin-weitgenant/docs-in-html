📦 docs-in-html — Arquitetura do Pacote

docs-in-html é um servidor de desenvolvimento zero-build para pastas de documentação em HTML puro. Ele gera automaticamente uma barra lateral (sidebar) em árvore a partir das suas pastas, oferece live reload e pan/zoom para diagramas Mermaid e SVGs. A filosofia: HTML em vez de Markdown — sem etapa de build.

💡 Você está lendo este documento dentro do próprio docs-in-html — os diagramas abaixo podem ser clicados para pan/zoom, e qualquer edição no arquivo dispara o live reload. Meta-documentação! 😄

Íncrivel, não?!?!

Visão geral

O pacote é dividido em duas metades que se conversam por rotas especiais:

  • Servidor (Node.js) — serve.js e amigos: servidor HTTP estático + injeção de scripts + watcher de arquivos.
  • Clientes (browser) — client/: scripts injetados nas páginas HTML que dão vida à UI (navegação, reload, zoom).

Os arquivos, um por um

serve.js servidor — o coração

Ponto de entrada (definido em bin no package.json). É um servidor HTTP construído sobre node:http, sem nenhuma dependência. Suas responsabilidades:

ResponsabilidadeComo
CLIParse manual de argv: docs-in-html [dir] [--port N] [--no-open], além do subcomando init. Abre o navegador com start/open/xdg-open conforme o SO.
Servir arquivosResolve a URL para um caminho dentro de ROOT, aplica a tabela MIME e envia o conteúdo. Valida o caminho para bloquear path traversal (403 fora de ROOT).
Injeção de scriptsTodo .html servido passa por injectScripts(), que insere tags <script> antes de </body> — o truque central do pacote (detalhes adiante).
ShellNa URL /, serve o index.html do usuário (se existir) ou o shell embutido de shell.js. Injeta <base href="/"> para o shell funcionar até em URLs profundas.
Rotas especiais/__manifest__ (árvore JSON), /__docs__/* (arquivos do cliente), /__delete__ (POST que apaga um doc) e o canal SSE do reload.
Deep linksSe o navegador navega top-level para /pasta/doc.html, o servidor devolve o shell envolvendo o doc (o iframe dentro do shell pede de novo, mas com header Sec-Fetch-Dest: iframe, e aí recebe o doc puro — sem recursão infinita).

manifest.js servidor — a árvore da sidebar

buildTree(root) percorre recursivamente a pasta de docs e produz o JSON que alimenta a sidebar:

  • Só inclui pastas e arquivos .html/.htm.
  • Ignora dotfiles, nomes com prefixo _, pastas vazias e o próprio index.html (que é o shell, não um doc).
  • humanize() transforma nomes de arquivo em títulos: auth-service.html → "Auth Service". Detalhe fino: usa String#toUpperCase por palavra (Unicode-aware) em vez de regex \b\w — senão integração viraria IntegraçãO.

reload.js servidor — live reload via SSE

createReload(root) devolve { handle, close }:

  • fs.watch(root, { recursive: true }) observa a pasta toda.
  • Debounce por arquivo (150 ms) — o Windows dispara vários eventos para um único save; o debounce os colapsa num só broadcast.
  • O broadcast usa Server-Sent Events: cada página conectada mantém uma resposta aberta em /__reload__ e recebe data: {"path": "..."} quando algo muda.
  • Se fs.watch não existir, degrada graciosamente: só avisa e segue servindo estático.

shell.js servidor — o layout embutido

Uma string com o HTML/CSS do layout padrão: cabeçalho, <aside> com <ul id="docList"> e um <iframe> para o conteúdo. O id="docList" é o contrato: é assim que o servidor e o nav.js reconhecem "esta página é um shell". Serve tanto como fallback (pasta sem index.html) quanto como scaffold do init.

init.js CLI — scaffolding

docs-in-html init [dir]: escreve o shell como index.html inicial para você customizar. Recusa-se a sobrescrever um index.html existente.

client/nav.js cliente — a sidebar viva

Injetado somamente em páginas com #docList (o shell). É o maior cliente e faz muita coisa:

  • Busca /__manifest__ e renderiza a árvore com pastas colapsáveis (estado lembrado em localStorage).
  • Clique num doc → carrega no <iframe> e sincroniza a URL com history.pushState (deep links funcionam, botão voltar também, via popstate).
  • Navegação dentro do iframe (load) → destaca o doc ativo e expande as pastas ancestrais.
  • Assinatura da árvore: a cada mudança de arquivo ele re-busca o manifest, mas só reconstrói o DOM se o conjunto de arquivos mudou — edições de conteúdo não resetam scroll/colapse/ativo.
  • Botão de esconder a sidebar e botão de excluir doc (dois cliques, com confirmação visual de 3 s, via POST /__delete__).

client/reload.js cliente — quando recarregar?

Injetado em todas as páginas. Abre um EventSource para /__reload__ e decide sozinho:

Mudou…ShellDoc no iframe

Bônus: cada mudança também é re-transmitida como CustomEvent("docs-in-html:change") na página — é assim que o nav.js (que não recarrega) fica sabendo que precisa re-buscar o manifest.

client/mermaid-zoom.js cliente — pan & zoom estilo mkdocs-material

Injetado com defer apenas em páginas com blocos Mermaid, <figure> com SVG, ou classes .panzoom/.diagram/.zoomable (e sem pan/zoom próprio). Clique no diagrama → lightbox com arrastar/scroll, botões +/−/ajustar e tela cheia. Carrega svg-pan-zoom do CDN sob demanda.

Dois detalhes de engenharia espertos:

  • Event delegation + pseudo-elemento CSS: o Mermaid reescreve o próprio DOM ao renderizar — listeners presos a nós internos morreriam. Delegação no document e um ::after no contêiner sobrevivem a qualquer reescrita.
  • Nunca sequestra cliques interativos: um SVG dentro de button, a, [onclick]… continua fazendo o que devia.

Fluxos

1. Requisição: do clique na sidebar ao doc renderizado

🔑 Note o Sec-Fetch-Dest: se o mesmo URL fosse aberto na barra de endereço (document), o servidor devolveria o shell em volta; vindo do iframe, devolve o doc puro. Uma requisição, dois comportamentos, zero recursão.

2. Live reload: do save no editor à página atualizada

3. Startup e a decisão de quais scripts injetar

Conceitos-chave para lembrar

  1. Zero build, zero dependências — só node:* builtin. Seu HTML é servido como está; a "mágica" (sidebar, reload, zoom) entra por injeção em tempo de resposta, nunca transformando seus arquivos em disco.
  2. O contrato #docList — shell é reconhecido por estrutura, não por URL. Permite shells customizados e deep links sem lógica especial.
  3. Reload seletivo — cada página recarrega só o que lhe diz respeito; o shell nunca se mata por mudanças alheias (preserva o estado da sidebar).
  4. Comunicação entre clientes via eventos DOM — o canal SSE alimenta o reload.js, que re-transmite como CustomEvent para o nav.js na mesma página.
  5. Sobreviver ao Mermaid — delegation + CSS pseudo-elemento em vez de listeners inline.

🧠 Quiz — cheque seu entendimento

Clique numa opção para ver se acertou (e a explicação).

1. Por que o docs-in-html não precisa de etapa de build, ao contrário de geradores como o MkDocs?

Porque ele converte o HTML para Markdown no servidor e volta para HTML no cliente. Porque os recursos extras (sidebar, reload, zoom) são injetados como tags <script> na resposta HTTP, sem alterar os arquivos em disco. Porque ele exige que os scripts sejam incluídos manualmente em cada página.

✅ A injeção acontece em injectScripts(), no momento de servir. Seus arquivos permanecem HTML puro — você poderia abrir qualquer doc direto no browser e ele ainda funcionaria (sem os extras, claro).

2. Quando o usuário digita /backend/api.html direto na barra de endereço, o que o servidor devolve?

Apenas o HTML puro do doc, sem sidebar. O shell (com sidebar), que por dentro carrega o doc num iframe — graças ao header Sec-Fetch-Dest: document da navegação top-level. Um erro 403, porque URLs profundas não são suportadas.

✅ Deep links funcionam: navegação top-level (Sec-Fetch-Dest: document) recebe o shell; a requisição do iframe dentro dele (Sec-Fetch-Dest: iframe) recebe o doc puro — sem recursão.

3. Você salva styles.css (usado pelos docs). O que acontece em cada página aberta?

Os docs abertos no iframe recarregam; o shell não recarrega (preserva colapso/scroll/ativo). Tudo recarrega, incluindo o shell. Nada recarrega: mudanças em CSS não são observadas pelo watcher.

✅ O watcher observa tudo; o client/reload.js decide: arquivos .js/.css compartilhados recarregam o doc em exibição, mas o shell só reage a si mesmo. Além disso o evento é re-transmitido como CustomEvent para a sidebar atualizar o manifest se a árvore mudou.

4. Como o nav.js evita perder o estado da sidebar (pastas colapsadas, scroll, doc ativo) quando você edita o conteúdo de um doc?

Ele salva o HTML da sidebar em localStorage a cada mudança e restaura depois. Ele nunca reconstrói a sidebar depois do primeiro render. Ele compara uma "assinatura" da árvore (conjunto de caminhos) e só reconstrói o DOM quando ela muda de fato.

✅ A função signature() serializa a estrutura (tipo + caminho de cada nó). Edição de conteúdo não muda a assinatura → sidebar intacta; criar/apagar/renomear arquivo muda → rebuild (com restauração do scroll).

5. Por que o mermaid-zoom.js usa event delegation em vez de adicionar listeners direto nos SVGs dos diagramas?

Porque listeners inline não funcionam dentro de iframes. Porque o Mermaid reescreve o próprio DOM após renderizar, o que destruiria listeners presos a nós internos; delegação no document sobrevive. Porque é mais rápido em páginas com muitos diagramas.

✅ Delegation no document + ícone de expandir via pseudo-elemento CSS ::after no contêiner: ambos sobrevivem a qualquer reescrita do DOM pelo Mermaid.

6. Qual é o papel do debounce de 150 ms no reload.js do servidor?

Colapsar os múltiplos eventos que alguns SOs (notoriamente o Windows) disparam para um único save, evitando recarregamentos duplicados. Aguardar o editor terminar de gravar o arquivo em disco antes de lê-lo. Limitar a taxa de requisições ao /__manifest__.

✅ Um save no Windows pode gerar vários eventos de watch para o mesmo arquivo. O timer por caminho garante um único broadcast por save real.

7. Como o manifest.js decide o que entra na sidebar?

Indexa todos os arquivos de texto e extrai os títulos dos <h1>. Segue um arquivo de configuração (nav.json) escrito pelo usuário. Varre a pasta recursivamente, incluindo só pastas (não vazias) e .html, ocultando dotfiles, prefixo _ e o próprio index.html.

✅ Convenção sobre configuração: qualquer pasta de HTMLs já "funciona" sem config. O index.html fica de fora porque é o shell, não um doc.

8. O canal de comunicação servidor→navegador para live reload usa qual tecnologia, e por quê (em vez de WebSockets)?

WebSocket bidirecional, para permitir excluir arquivos pelo chat. Server-Sent Events (uma resposta HTTP mantida aberta em /__reload__) — unidirecional e simples, que é tudo que o reload precisa. Polling de fetch a cada segundo.

✅ SSE é o ajuste perfeito para "servidor avisa cliente": uma conexão HTTP normal, sem upgrade de protocolo, com reconexão automática pelo EventSource.

9. O que identifica uma página como "shell" para o servidor e para o nav.js?

A presença de um elemento com id="docList" na página — um contrato estrutural, não baseado em URL. Estar servida exatamente na URL /. Ter a meta tag <meta name="docs-shell">.

✅ Estrutura > URL: após um F5 num deep link, o shell vive em /pasta/doc.html e continua sendo reconhecido pelo #docList. Shells customizados funcionam de graça.

10. Por que npx . docs-html (a task do VS Code) funciona sem instalar nada globalmente?

Porque o npx sempre executa o server.js da pasta atual. Porque o serve.js se auto-registra no PATH na primeira execução. Porque o package.json declara bin: { "docs-in-html": "serve.js" }, e o npx resolve comandos do pacote local.

✅ O campo bin torna o pacote executável; o npx, rodando na pasta do pacote, cria o shim para docs-in-html apontando para serve.js e repassa docs-html como diretório a servir.
