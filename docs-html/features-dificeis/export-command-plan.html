1. Background — como o pacote funciona hoje

O docs-in-html é um servidor dev zero-build: você aponta pra uma pasta de HTMLs e ganha uma UI com sidebar em árvore, live reload e pan/zoom de Mermaid/SVG. Ele é enxuto — quatro arquivos no servidor e três clientes:

ArquivoPapel
serve.js (~370 linhas)Servidor HTTP, roteamento, CLI (serve/init), injeção de scripts, endpoints de mutação (delete, rename, mkdir, order)
manifest.jsbuildTree(root) — varre a pasta e monta a árvore (pastas + .html, esconde dotfiles, _-prefixos e index.html); aplica ordem manual de _order.json e ícones de pasta de _icons.json
shell.jsO HTML do shell embutido (header + sidebar + iframe), usado quando não há index.html na pasta
reload.jsWatcher de arquivos + canal SSE /__reload__
client/nav.js (~880 linhas)Renderiza a sidebar a partir de fetch("/__manifest__"); active highlight, colapso de pastas, drag-and-drop, delete, rename, mkdir, gravação de ordem
client/reload.jsCliente SSE — reconecta e dá location.reload() ao receber evento
client/mermaid-zoom.jsPan/zoom (e fullscreen) para blocos Mermaid e SVGs

Quatro comportamentos só existem com o Node rodando:

1 · Manifest dinâmiconav.js faz fetch("/__manifest__") — endpoint gerado em runtime por buildTree.
2 · Injeção de scriptsserve.js espeta <script src="/__docs__/..."> nos HTMLs na resposta (com heurística: nav só no shell, zoom só se há Mermaid/figure).
3 · Deep URLsVisita top-level a /docs/foo.html recebe o shell com o doc dentro do iframe, via header Sec-Fetch-Dest: document.
4 · Edição pela sidebarDelete (/__delete__), rename/move (/__rename__), criar pasta (/__mkdir__) e drag-order persistido (/__order__ → _order.json) — tudo depende de POSTs ao servidor.
Termo-chave: o shell é a moldura (header + sidebar + iframe). O doc é o HTML do usuário, carregado dentro do iframe. O servidor dev decide qual dos dois entregar para cada request; um host estático entrega sempre o arquivo cru.

2. O problema com o Surge

Surge (como GitHub Pages, Netlify drop etc.) só serve arquivos. O resultado ao subir a pasta crua:

FuncionalidadeNo NodeNo Surge
Sidebar / árvoreokquebra — fetch("/__manifest__") dá 404; o catch engole e a sidebar fica vazia
Pan/zoom Mermaidokquebra — HTML servido cru, sem <script> injetado
Live reloadokfalha silenciosa — EventSource não reconecta pra sempre; inofensivo, mas desnecessário
Links profundos (deep URL)okquebra — sem o wrap server-side, /docs/foo.html abre o doc sem shell
Edição na sidebar (delete, rename, mkdir, reorder)oksem sentido — dependem de POST /__delete__, POST /__rename__, POST /__mkdir__ e POST /__order__

As duas saídas possíveis são: (B) deploy onde Node roda (Render, Railway, Fly.io — o $PORT já é respeitado, zero mudança), ou (A) um passo de exportação que congela tudo que hoje é dinâmico. Este plano implementa a Opção A: ela é mais no espírito do pacote (zero-build no dev, zero-server no deploy) e vira um feature real, não um workaround.

3. A intuição do export

A ideia central: o que o servidor decide em runtime, o export decide uma vez e escreve em disco. Cada comportamento dinâmico tem um equivalente estático direto:

Runtime (serve)Export (uma vez)
GET /__manifest__arquivo manifest.json na raiz do output
<script src="/__docs__/nav.js"> injetado na respostamesma tag escrita dentro dos HTMLs + cópia de client/ para __docs__/
Serve client/ em /__docs__/*client/* → __docs__/* (cópia física)
Wrap do shell em deep URL (header Sec-Fetch-Dest)não é preciso: o shell no output aponta o iframe pro doc via query/hash, e os docs funcionam tanto dentro do shell quanto sozinhos
reload.js sempre injetadoomitido no export (não há o que recarregar)
flowchart LR subgraph hoje ["Hoje — cada request"] A[pasta de HTMLs] --> S["serve.js\n(Node)"] S -->|"injeta scripts\n+ /__manifest__ + wrap"| B[navegador] end subgraph export ["Com export — uma vez"] A2[pasta de HTMLs] --> E["docs-in-html export"] E --> O["dist/\nHTMLs já com tags\n+ manifest.json\n+ __docs__/"] O -->|"arquivos crus"| C[Surge] C --> B2[navegador\nidêntico ao dev] end

Exemplo concreto. Antes de um doc arquitetura.html (com um Mermaid) chegar ao navegador, o serve.js espeta antes do </body>:

<script src="/__docs__/reload.js"></script>
<script src="/__docs__/mermaid-zoom.js" defer></script>

Depois do export, o dist/arquitetura.html já nasce com a tag de zoom gravada no arquivo (e sem a de reload). O shell exportado (dist/index.html) nasce com a tag do nav.js. Nada de runtime — só arquivos.

Ponto de elegância: a heurística de injeção já existe (injectScripts em serve.js) e o nav.js já é um no-op sem #docList, com fallback estático. O export reaproveita essas peças — o código novo é basicamente "escrever em arquivo o que hoje se escreve na resposta HTTP".

4. Mudanças — arquivo por arquivo

Novo: export.js (o coração do plano)

Um módulo novo, chamado pela CLI quando o subcomando é export. Recebe a pasta de origem e um diretório de saída (default ./dist). Ele orquestra cinco passos, cada um deles já com peça pronta no código atual:

  1. Copiar tudo — replica a pasta de docs para o output (exceto o próprio diretório de saída, para não se copiar recursivamente).
  2. Gerar o manifest — chama o buildTree existente sobre a origem e escreve manifest.json na raiz do output. Bônus: como o buildTree já aplica _order.json (ordem manual de drag) e _icons.json (ícones de pasta), o manifest exportado sai pronto, com a mesma ordem e ícones do dev — desde que esses _-arquivos existam na origem (eles são copiados no passo 1: ficam ocultos da sidebar, mas existem em disco).
  3. Copiar os clientes — client/ inteira para __docs__/ no output (inclui sidebar-left.svg que o nav.js referencia).
  4. Reescrever os HTMLs — reutiliza a mesma lógica do injectScripts, mas com duas diferenças: escreve no arquivo em vez de na resposta, e sem a tag de reload. Aplica ao shell exportado (nav.js) e a todos os outros HTMLs (mermaid-zoom.js quando a heurística dispara).
  5. Garantir shell — se não há index.html na origem, escreve o SHELL embutido como index.html do output (com a mesma injeção de nav.js).

client/nav.js — trocar a fonte do manifest

Dois fetch("/__manifest__") viram uma fonte configurável: /__manifest__ no dev, /manifest.json no export. A forma mais simples de distinguir: o export injeta uma pequena flag global antes do script, e o nav.js lê essa flag para escolher a URL. Sem flag, comportamento atual — inofensivo para quem usa só o servidor.

client/nav.js — modo somente-leitura fora do dev

Hoje a sidebar é uma UI de edição completa: cada item tem botão de excluir (POST /__delete__), pode ser renomeado/movido (POST /__rename__), pastas podem ser criadas (POST /__mkdir__) e o drag-and-drop persiste a ordem (POST /__order__ → _order.json). No export nada disso existe. Quando a flag indicar modo estático, o nav.js entra em modo somente-leitura: além de trocar a URL do manifest, ele não renderiza botão de delete, não abre prompt de rename, não cria pastas e não inicia drag-and-drop (ou falha quieto — mas esconder é mais limpo). Como os handlers ficam atrás da mesma flag, é um único ponto de decisão, não quatro.

serve.js — CLI e deduplicação

Três ajustes: parsear o novo subcomando export [dir] [--out DIR] (o padrão de argumentos já suporta init, então segue o mesmo molde); delegar ao export.js; e idealmente extrair a lógica de injeção para um lugar compartilhado (um módulo inject.js ou exportar a função de serve.js), para que dev e export usem exatamente a mesma heurística — um fix num lugar, não dois.

reload.js / shell.js / manifest.js

Nenhuma mudança. O watcher e o SSE continuam exclusivos do modo dev; o shell e o buildTree são consumidos como estão. Isso é sinal de bom desenho: o export é uma nova consumidora das peças existentes.

Docs e DX

Atualizar o help da CLI e o README com o fluxo de duas linhas: docs-in-html export → surge dist. Vale registrar também o comportamento esperado com deep URLs no export: o shell é a porta de entrada; um doc aberto direto funciona standalone (com zoom, sem sidebar — que é do shell).

Ordem sugerida de implementação

  1. export.js com cópia + manifest + clientes (o esqueleto já entrega valor: sidebar funciona).
  2. Injeção de tags nos HTMLs do output (zoom nos docs).
  3. Flag de modo no nav.js (URL do manifest + modo somente-leitura: sem delete, rename, mkdir nem drag-order).
  4. CLI + help + README.
Caso extremo a lembrar: a injeção atual usa /__docs__/... com barra absoluta. Como o export preserva esse layout na raiz do output, os links continuam válidos em qualquer subdomínio do Surge — desde que o site seja publicado a partir da raiz (o que surge dist faz por padrão). Se alguém hospedar num subcaminho (user.github.io/projeto/), seria preciso uma passada extra de reescrita de caminhos — fora do escopo deste plano, mas bom deixar documentado.
