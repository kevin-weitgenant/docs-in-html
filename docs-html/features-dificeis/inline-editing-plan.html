1. Background — o que existe hoje

O fluxo atual do docs-in-html: o serve.js serve cada HTML enriquecido na resposta — ele espeta tags <script> (zoom, reload) antes do </body>. Isso significa que qualquer script cliente já roda dentro do documento do usuário, com acesso total ao DOM renderizado. A edição inline se encaixa exatamente nesse mecanismo: um novo script client/edit.js, injetado como os outros.

Dois fatos da arquitetura importam aqui:

Fato 1 · O servidor é NodeJá existe servidor com acesso a fs (o botão delete já faz POST /__delete__). Salvar o arquivo editado é um endpoint irmão: POST /__save__.
Fato 2 · Watcher + SSEO reload.js já detecta mudanças no disco e recarrega. Ao salvar via editor, o próprio reload dispara — feedback visual de graça.
Termo-chave: WYSIWYG — "what you see is what you get". O usuário edita o texto renderizado (negrito aparece negrito, código aparece em monospace) e o navegador guarda a estrutura HTML por baixo. É o mesmo modelo do Notion, do Medium e do Google Docs.

2. A intuição — contenteditable é a resposta

A pergunta central do usuário — "quero clicar em qualquer texto e editar, sem ver tags" — tem uma resposta que o próprio navegador dá, nativa, desde 2010: o atributo contenteditable. Quando um elemento recebe esse atributo, seu texto vira editável no lugar, com cursor, seleção e teclado — exatamente como um input, mas preservando toda a formatação visual. O usuário nunca vê HTML porque nunca sai do modo renderizado.

docs/arquitetura.html ✏ Editando

O serve.js serve cada HTML enriquecido na resposta — e agora editável. O usuário clicou na frase e está digitando.

O fluxo completo, do clique ao arquivo em disco:

sequenceDiagram participant U as Usuário participant D as Doc (edit.js no iframe) participant S as serve.js participant F as arquivo .html U->>D: clica no toggle "Editar" D->>D: body.contentEditable = true + outline nos elementos U->>D: clica num parágrafo, digita, corrige U->>D: clica em "Salvar" (ou Ctrl+S) D->>S: POST /__save__ { path, html: document.documentElement.outerHTML } S->>F: fs.writeFile (arquivo original, sem o script injetado) F-->>D: watcher detecta → SSE → reload D-->>U: página recarrega já com o novo texto
O detalhe que salva o projeto: o navegador não sabe quais tags foram injetadas pelo servidor e quais são do autor. Antes de serializar, o edit.js marca as tags injetadas (ex.: atributo data-injected) e as remove do outerHTML enviado — o arquivo em disco recebe só o conteúdo editado, byte a byte limpo das ferramentas do viewer.

3. Viabilidade — o que é fácil, o que é chato, o que é difícil

Resposta curta: muito realizável — nível de dificuldade 6/10, acima do export (que era reaproveitamento puro) mas abaixo de qualquer editor rico. A divisão:

PeçaDificuldadePor quê
Toggle "Editar" + contenteditable no bodytrivialUma linha de JS liga/desliga; outline CSS sinaliza o que é editável
Endpoint POST /__save__fácilIrmão direto do /__delete__ existente; validação de path igual (sem escapar da raiz)
Remover tags injetadas antes de salvarmédiaFácil de marcar (data-injected); o cuidado é não esquecer de nenhuma (reload, zoom, edit)
Feedback de "não salvo" / atalho Ctrl+SmédiaBeforeunload + indicador no toggle; UX, não tecnologia
Serialização fiel (o HTML salvo = o HTML original + edição)chatoO parser do navegador pode reordenar atributos, normalizar entidades e reformatar &. Para docs, inofensivo — mas o diff do git fica maior na primeira edição
Editar dentro de blocos pre/code sem quebrarchatoEditável funciona, mas indentação/enter podem inserir tags novas; mitigável com plaintext-only nesses blocos
Editar blocos Mermaid / diagramasdifícilA fonte é texto D2/Mermaid dentro de <pre> — editar o renderizado não faz sentido. Decisão proposta: não editável por ora, ou abrir o pre fonte num editor simples
Editor rico (negrito, listas, links via toolbar)fora do escopodocument.execCommand cobre 80% com 3 linhas, mas é API legada. A proposta assume edição de texto; formatação nova fica pra depois
Por que a serialização é aceitável: o outerHTML do documento editado é HTML válido por construção — o parser do navegador já normalizou tudo ao carregar. O risco não é corromper o arquivo; é apenas o diff ruidoso. Para uma pasta de docs mantida por uma pessoa, isso é um trade-off honesto: a edição inline substitui abrir o arquivo no editor de texto.

4. Mudanças — arquivo por arquivo

Novo: client/edit.js (o coração)

Injetado em todos os HTMLs (diferente do zoom, que é heurístico). Responsabilidades: renderizar o toggle no canto superior direito (fixed, discreto, fora do fluxo do documento — num <div> próprio para não poluir o corpo); ligar contenteditable no body ao ativar e desligar ao salvar/cancelar; marcar visualmente os blocos sob o cursor (outline); interceptar Ctrl+S; e ao salvar, clonar o documento, remover as tags injetadas e do próprio editor, serializar e mandar via fetch pro endpoint. Bloqueia saída com mudanças não salvas.

serve.js — endpoint /__save__ e flag de modo

Um handler POST irmão do /__delete__: recebe o caminho relativo (mesma validação — recusa .. e caminhos fora da raiz) e o HTML serializado, e escreve no arquivo original com fs.writeFile. Importante: o watcher vai disparar o reload do próprio editor — o edit.js pode suprimir um ciclo ignorando o primeiro evento após salvar. Também passa a marcar as tags que injeta com data-injected (mudança de uma linha na injeção existente).

Compatibilidade com o export

HTMLs exportados são estáticos: sem servidor, não há onde salvar. Mesmo mecanismo da flag de modo estático (planejada no plano do export): sem servidor, o edit.js não é injetado — ou o toggle aparece desabilitado com tooltip "edição disponível apenas no modo dev". Zero custo extra.

Ordem sugerida de implementação

  1. edit.js mínimo: toggle + contenteditable + Ctrl+S salvando via /__save__ (já entrega o valor central).
  2. Limpeza das tags injetadas no outerHTML (data-injected).
  3. Guard rail: beforeunload com mudanças pendentes + supressão do reload pós-save.
  4. Refinamentos: plaintext-only em pre/code, indicador "não salvo" no toggle, esconder em modo estático.
